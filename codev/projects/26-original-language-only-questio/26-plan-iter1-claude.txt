**3. The metadata channel as described cannot deliver `ask_as` to the prompt renderer.**
Phase 1 says the three fields reach `generate` via "the `license_for_standardized_path` analog". But `license` never travels *into* `generate()` — it is a **path filter**: `filter_standardized_paths()` returns kept paths, then `schema.load_documents(kept)` **discards the path→doc association**. Meanwhile `_build(task, doc, entry)` (generate.py:102) has only a `Document`, and `Document` (schema.py:52-59) carries no catalogue facts. So a path-keyed recovery function structurally can't feed `ask_as`/`citation_hint` to the renderer. `original_language` *can* be a path filter; the other two cannot.

The clean mechanism is already implied by the spec's own slug-agreement rule: `Target.slug == _slugify(f"{work}-{version}-{language}")` — exactly the tuple Phase 2 groups "texts" on, and converters set `doc.work/version/language` from the target. So Phase 1 should deliver something like `text_metadata(sources) -> dict[tuple[str,str,str], TextMeta]` (fail-closed: a doc whose tuple is absent raises `CatalogueError`), passed into `generate()` as a parameter. Worth pinning in the plan — getting it wrong costs rework across Phases 1 **and** 2.

**4. `verify_source` question identity is a spec requirement with no plan coverage.**
Spec Constraints require: the question belongs to the **asked** edition, `source` records the asked edition, and `expected` gains `true_version`. Current code does the opposite — `_source_dict(doc, entry)` records the *passage's* doc, `expected` has only `true_work` (generate.py:120), the prompt interpolates a raw `neg_work` string (no `ask_as`), and negatives are selected at **work** granularity (`works`, `work_texts`) rather than `(work, version, language)`. Phase 2 says only "keep `verify_source` negative sampling + the existing deterministic negative share," which reads as *no change*. This is also a silent cross-phase hazard: Phase 3's `by_text` aggregates off `question.source`, so if Phase 2 doesn't invert the source dict, the per-text table mis-attributes every negative.

Relatedly, the risk-table mitigation **"prefer cross-work/cross-family negatives" is currently a no-op** — the nine hadith collections *are* nine distinct `work` values, so cross-work pairing is exactly what already happens and exactly what produces variant-narration false "no"s. A real mitigation needs a family/grouping notion (e.g. never pair two hadith collections) that the plan would have to define.
