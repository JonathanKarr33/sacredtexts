## One real finding: the iteration-2 `parse_yes_no` fix over-corrected

Codex's iter-2 issue was legitimate, but the fix swapped a narrow false positive for a broader false-negative class. `parse_yes_no` now returns `None` whenever **both** tokens appear *anywhere* in the normalized answer. Probed live:

```
'Yes, there is no doubt that this passage is from John 1:1.' → None → incorrect
'Yes. No other work contains this wording.'                 → None → incorrect
```

Both are unambiguous leading commitments that previously scored correct. "no" is a common English word ("no doubt", "no other", "there is no"), so this class is plausibly *more* frequent in real answers than the ambiguous-decline case it fixed. It also contradicts the module docstring's own contract (line 29: "parsed **leading** Yes/No equals expected"; line 43 still says "uses the first Yes/No token" — now stale).

This matters beyond the committed evidence: `verify_source` false-premise negatives are a core part of the Phase-1 question (`generate.py:51`, `--negatives-share`), so a future run will hit it.

**Suggested narrower rule**, which still kills codex's case: keep "first token wins," but return `None` only when the tokens are adjacent in an explicit non-commitment idiom — `yes or no` / `yes/no` / `yes and no`. That's a one-line regex pre-check plus two tests (`"Yes, there is no doubt…"` → `"yes"`; `"…whether the answer is yes or no"` → `None`). Zero rebaseline impact either way.

I did not modify anything to test this — the probe ran `score_answer`/`parse_yes_no` read-only on throwaway inputs in `/tmp`.
