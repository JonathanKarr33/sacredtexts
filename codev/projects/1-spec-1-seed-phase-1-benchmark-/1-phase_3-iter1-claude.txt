## Findings (none blocking)

1. **The one test I'd add before moving on.** Nothing pins "skipping an empty line must not renumber later lines," yet that property is load-bearing at **207 real places**. A one-token regression (incrementing `line_no` only on kept lines) would silently shift hundreds of Talmud citations — precisely the silent-citation-drift class that cost Phase 2 three iterations, and the aggregate assertions (first citation + entry count) would all still pass. `_talmud("T", [[], [], ["<b></b>", "real"]])` → expect `T 2a:2` locks it in 4 lines.

2. **No language/version cross-check.** `convert_sefaria_talmud` ignores each file's own `language` and `versionTitle`. The `he` target is safe only by glob convention; if that glob ever widens, English tractates get silently labelled `he`. A `data["language"] != target.language → ConvertError` guard is two lines and fits the fail-fast principle.

3. **Weaker guard in `hadith_sunnah`**: `if number is None` (no `isinstance`), so a non-int `idInBook` would stringify into a citation — inconsistent with the `isinstance` rigor elsewhere in the file.

4. **Misleading diagnostic**: `_require_unique_citations(entries, str(paths[0]))` in the merged Talmud/NABRE path always names the *first* file, even if tractate #30 caused the duplicate.

5. **Silent drops aren't reported**: 125 empty Malik hadiths and 207 markup-only Talmud lines vanish with no count. Behaviorally right (empty units can't be items), but a "skipped N empty units" echo per target would make conversion auditable for the Phase 8 evidence story.

6. **Plan text now stale** (deviation is defensible and recorded in the thread): plan says Quran citation `surah:ayah` and hadith "collection + number"; the implementation prefixes the work (`The Qur'an 1:1`), consistent with the Phase-2 self-identifying-citation decision.

7. **Scale heads-up for Phase 5, not Phase 3**: Talmud en is a single **47 MB / 78,117-entry** document; the full standardized tree is 151 MB and `schema.load_documents` is fully in-memory. The spec permits sharding ("one document per Bible book"); worth deciding before `generate` runs corpus-wide. Note the CLI's `len(docs)==len(paths)` stem heuristic would also need care if Talmud were sharded, since dedup breaks that equality.
