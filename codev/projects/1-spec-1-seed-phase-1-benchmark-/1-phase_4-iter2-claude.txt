## Non-blocking findings (verified, with repro)

1. **`roundtrip_ok` can't see in-place entry mutation (aliasing).** `assemble` passes `Entry` references through, and `Entry` is a mutable dataclass. An assembler that rewrote `e.text` in place mutates the shard's own object, so the comparison is against already-corrupted input. Probe: a `text`-lowercasing assembler → `roundtrip_ok: True` with the shard text visibly changed. Fix is one line: deep-copy `docs` before assembling inside `roundtrip_ok` (or `replace()` entries in `assemble`).
2. **`unit_type` is outside the round-trip key.** The position key is `(citation, text)`; an assembler that set every `unit_type = "WRONG"` → `roundtrip_ok: True`. Since `unit_type` is part of the interchange entry the spec calls lossless, consider `(unit_type, citation, text)` in both the dedup key and the position key.
3. **The duplicate-citation error path is quadratic.** `dupes = sorted({c for c in citations if citations.count(c) > 1})` (export.py:104) is O(n²). Measured: **11.2s** to raise on a 40k-entry key; Talmud-en is 78k entries (~45s). Fail-fast should also be fail-fast to *report* — `collections.Counter` makes it O(n).
4. **Shard ordering is safe today but fragile for future shardings.** Ordering shards by first citation is honestly documented and gives OT→NT for the one real multi-shard work. If a converter ever shards per book, the assembled order becomes alphabetical ("1 Chronicles, Acts, Amos…"), not canonical. An optional `order` hint on the catalogue target would future-proof it — worth a note, not work now.
5. **Dedup can produce a misleading round-trip failure.** If two shards of one key overlap in *different relative orders*, dedup keeps the first occurrence and the second shard's strictly-increasing check fails — reported as "does not reproduce its shards" rather than "shards disagree on ordering". No real data hits this; a clearer message would help if it ever does.
6. **Minor:** the CLI exits 1 on round-trip failure (`cli.py:149`), not exit 2 as the rebuttal states; and `export`'s restricted-input filtering is untested (it reuses the well-tested `filter_standardized_paths`, so this is low risk).
