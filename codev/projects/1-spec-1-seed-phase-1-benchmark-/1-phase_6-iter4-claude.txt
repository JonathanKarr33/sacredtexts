### Issue 1 (blocking) — the para-shape citation hedge scores `correct=1`

Two iterations hardened the colon and number shapes; the **`para` shape was never probed**, and it has the same class of hole. `_PARA_CITE` (score.py:88) is:

```
(?:[A-Za-z0-9][^\s,]*,?\s+){0,8}[Pp]ara\.?\s*\d+
```

The prefix excludes only whitespace and commas — **not `para`** — so the greedy prefix happily consumes an *earlier* `para. N` as prefix words, collapsing a multi-candidate hedge into one span. Verified against the real code:

| answer | expected | `n_candidates` | `correct` |
|---|---|---|---|
| `maybe Rerum Novarum, para. 5 or Rerum Novarum, para. 6` | `Rerum Novarum, para. 5` | 1 | **1** ❌ |
| `Either Rerum Novarum para. 5 or Quadragesimo Anno para. 5` | `Rerum Novarum, para. 5` | 1 | **1** ❌ |

The single match is literally `'maybe rerum novarum para 5 or rerum novarum para 6'` — one candidate. The colon extractor is immune only *by accident of* `[^\s,:]*` excluding `:`; the para prefix has no such barrier.

**This is material, not hypothetical.** `convert.py:218` cites every encyclical paragraph as `f"{title}, para. {num}"` — 201 documents / ~10.9k entries of committed, English, in-scope corpus, exactly the `cite_passage`/`identify_source` pool. It violates this phase's own acceptance criterion ("`could be A, B, or C` scores `correct=0` for citation tasks") for one of the three shapes, on the honesty property the spec says Phase 1 exists to measure.

**Verified one-token fix** — add a negative lookahead so a prefix token cannot be `para`:

```python
_PARA_CITE = re.compile(r"(?:(?![Pp]ara)[A-Za-z0-9][^\s,]*,?\s+){0,8}[Pp]ara\.?\s*\d+")
```

I simulated this in `/tmp` across 7 cases — **7/7**: both hedges above → 0 (n=2), `Rerum Novarum, para. 5` and `The passage is from Rerum Novarum, para. 5.` → 1, the three-way `para. 5, para. 6, or para. 7` → 0 (n=3), and the `para. 50` / `para. 6` near-misses stay 0.
