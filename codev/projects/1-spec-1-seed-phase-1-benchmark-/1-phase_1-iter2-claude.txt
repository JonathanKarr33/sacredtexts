## Findings (none blocking)

**1. `convert`'s raw-path gate is still fail-open for out-of-catalogue paths.** `license_for_raw_path` returns `None` for an unmapped file, and the gate only refuses `== "restricted"`. Concretely: the NABRE target's glob is exactly `nabre.json`, so `texts/raw/Roman Catholic/nabre (1).json` is both git-trackable and convertible with no flag and no warning. This is the inverse of the standardized side, which you deliberately made fail-closed. I accept your argument that catalogue-driven `convert` is Phase 2 — but please make Phase 2's `convert_target` resolve inputs *only* from catalogue targets, so the hole closes rather than persisting behind a now-asymmetric gate.

**2. README drift that the new fail-closed path makes user-visible.** Step 1 still writes to `texts/bible-nabre.json` / `texts/encyclicals/` (both gitignored and declared "legacy, superseded"), while step 3 now reads `texts/standardized` with path-based license recovery. Following the README verbatim: nothing lands in `texts/standardized`, then `generate texts/standardized` hits `expand_json`, which appends a *nonexistent* path unchanged (`is_dir()` is False) and fail-closes with `not under any catalogue target's standardized directory … refusing (fail-closed)`. Loud, but it reports "you haven't converted anything yet" as a license-verification failure. Two cheap fixes: distinguish *path absent / no documents found* from *exists but unmapped*, and point step 1 at the `standardized_dir` convention (or mark it "Phase 2").

**3. `license_for_standardized_path` tie-breaks by first-at-max-depth, not most-conservative** — unlike `build_raw_license_index`, which deliberately lets `restricted` win. I checked for live collisions: the only one is the intentional LDS OT/NT pair, and both are `public-domain`, so there's no fail-open today. But it's a latent copyright hazard, and slug collapse makes it more reachable than it looks (`ASV (1901)` → `asv--1901-`). Two one-liners remove the class: prefer `restricted` on ties, and assert at load that colliding `(source_id, slug)` targets agree on license.

**4. `fetch_date: unknown` discards a date the repo already knows.** Sunni Islam, Judaism, and LDS all record `unknown`, yet `texts/README.md` states these came from the working group's Box folder "Phase I / raw JSON", **downloaded 2026-10-10** — and `retrieved_from` names only the upstream (sefaria.org, QUL, sunnah.com, Ben Crowder), omitting the Box channel that was the actual fetch. The spec asks for "where it came from, how it was fetched, fetch date". Recommend `fetch_method: working-group Box drop (Phase I / raw JSON)`, `fetch_date: "2026-10-10"`, upstream attribution staying in `retrieved_from`/`notes`, and reserving `unknown` for the genuinely unknown *upstream* generation date. Honest either way — but currently less informative than the evidence allows.

**5. Minor: `yaml.safe_load` errors aren't wrapped.** A syntactically broken `source.yaml` escapes as `yaml.YAMLError`, which `main()`'s handler doesn't catch — traceback + exit 1 instead of `error: …` + exit 2. PyYAML's mark does name the file so it is loud, and no test covers malformed-YAML (as distinct from malformed-schema).

**6. Minor: `_slugify` leaves doubled hyphens** (`the-bible-asv--1901--en`, `septuagint---greek-new-testament-tlg-grc`). Collapsing runs of `-` is cheaper *now* than after Phase 2 writes those directories — once standardized dirs exist, the slug function is load-bearing for license recovery and changing it orphans them.

**7. Note for Phase 2**: `encyclicals/index.json` is under no target's payload glob, so it carries no catalogue license. Harmless today, but a catalogue-driven convert that expands the encyclicals directory will pick it up.
