### Issue 1 — the anti-hedge is numeric-only; cross-book hedges still score 1 (score.py:74-86)

`_citation_candidates` strips the work/book name and keys on the numeric token, and `correct` is still decided by **raw containment**, with the candidate count only used as a veto. So a hedge whose candidates share verse numbers passes. Verified:

| answer | expected | `correct` |
|---|---|---|
| `It could be Jude 1:3, Jude 1:4, or Jude 1:5.` | `Jude 1:3` | 0 ✅ (spec's literal example) |
| `It could be John 1:1, Genesis 1:1, or Micah 1:1.` | `John 1:1` | **1** ❌ |
| `Either Jude 1:3 or John 1:3.` | `Jude 1:3` | **1** ❌ |

The spec's requirement is that "a single citation candidate is extracted … so **containment alone cannot game** the provenance-honesty property Phase 1 exists to measure." Here containment is still the decider. `John 1:1 / Genesis 1:1 / Micah 1:1` is a realistic hedge shape, not a contrived one.

Fix: extract candidate **spans including the leading work/book tokens** (an optional capitalized-word prefix before the numeric token — citations are `<Book> c:v`, `Berakhot 2a:1`, so this is tractable), then set `correct = (len(candidates) == 1) and normalize(candidate) == normalize(expected)`. That makes "single extracted candidate equals ground truth" literal rather than approximated, and kills the hole. The existing hedge tests (test_score.py:110-124) only use numerically-distinct hedges, so they give false confidence — add the cross-book case.

### Issue 2 — `identify_version` doesn't match the contract and is gameable (score.py:101-102)

Spec table: `identify_version` metrics are **exact, normalized (on label)**. The implementation emits only `correct`, computed by containment. Consequences:

- `"That is not the KJV; it is the ASV."` scores **correct=1** against expected `KJV` — a flatly wrong answer.
- `"KJV, ASV, or WEB"` scores 1 for *every* version-gated item.

This is reachable: Phase 5 deliberately made `identify_version` live for the Bible via KJV/ASV/WEB. Since Phase 6's design decision is "each task's applicable metrics match the spec table," this task needs label `exact`/`normalized` and a correctness rule based on label equality (or single-candidate extraction over the corpus's known version labels), not substring presence.
