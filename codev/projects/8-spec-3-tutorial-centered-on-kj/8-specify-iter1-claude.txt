### Issues that should be fixed before approval

1. **Live web search introduces a new copyright exposure the spec never addresses — and the audit cannot catch it.** A search-enabled model asked for a Talmud daf or a Bible verse can return a *copyrighted* translation it found on the web (Steinsaltz English, NABRE, NA28), and those answers get committed to a **public** repo. `audit.py`'s origin layer keys on the *question's* source (public/open → passes), and its content layer only fires when restricted payloads are present locally. The project's #1 critical fact is the copyright gate; this spec commits model-generated web-retrieved text for the first time. The spec needs an explicit treatment: a Risks row, and a success criterion or constraint on how the committed search-on answers are cleared (e.g. a documented spot-check, or restricting the committed run's answer content).

2. **`audit.py :: _norm` is Latin-only, so the content layer is a no-op on Arabic/Hebrew.** Verified: `_norm(<vocalized basmala>)` → `''` and `_norm(<Greek John 1:1>)` → `''` (so `len(n) >= 60` never holds). Your criterion "`audit runs/<id>` passes" will pass *trivially* for the non-Latin majority of the committed run. A spec whose whole point is fair non-Latin handling should either extend `_norm` alongside `normalize()` or state the limitation explicitly as out of scope with reasoning.

3. **Web-search cost accounting is unaccounted for.** `providers.py :: _anthropic_usage` extracts only `input_tokens`/`output_tokens`. Anthropic bills server-side web search per request and reports it under `usage.server_tool_use.web_search_requests`. With `price_in`/`price_out` set, the committed run's cost table would understate the true cost — against this codebase's explicit norm that a partial number must not "masquerade as the run's cost" (`score.py:356`). Say whether search-request usage is captured or explicitly excluded (and if excluded, how the artifact says so).

4. **The headline metric may confound the very contrast you want to display.** `retrieve_quote`'s `correct = normalized` is whole-answer equality. A search-enabled model is *more* likely to append attribution/citation prose, so search-on can score **lower** on the headline while being materially better at retrieval. The spec is right that this is a result to display, not assert — but it should name the hazard and state that `token_f1`/`exact` are the discriminating numbers, so the plan doesn't "fix" it by quietly changing the `_SUBMETRICS` contract (which req 4 forbids).

### Smaller points (not blocking)

- **"no duplicate-id or unknown-key error" is inaccurate**: `config.py :: load_config` performs no unknown-key validation at all — a `tools:` key in YAML is silently ignored today. So the criterion as written would pass *before* the feature is implemented. Restate it as "the `tools` setting is parsed into `ModelSpec` and honored", and consider strict unknown-key rejection (fail-fast norm).
- **Approach A degrades the panel's own stated purpose.** `score.py:361` documents `panel` as committed-artifact *proof* of what ran; a marker-bearing `panel.model` is no longer the true API model string. Cheap fix with zero viewer change: also emit the raw string under a key the viewer ignores (e.g. `api_model`), so the proof stays truthful.
- **The tutorial's `--tasks` set is never pinned.** Today's tutorial is `--tasks retrieve_quote`; the criteria imply the same but don't say so. Worth stating, because **`generate.py` imports `normalize` from `score`** (for `work_texts` / `version_texts`) — so the normalization change has a *generation-side* blast radius on `verify_source` negatives and `identify_version` ambiguity for non-Latin corpora. (Latin/first-run determinism is safe: `_qid` hashes raw text, and Latin output is unchanged.)
- `MIN_WORDS_IDENTIFIABLE = 12` silently excludes short ayahs from the Qur'an pool. Not a defect — the pool is ample — but the committed run's Arabic items will skew long; worth a line so it isn't mistaken for a bug later.
