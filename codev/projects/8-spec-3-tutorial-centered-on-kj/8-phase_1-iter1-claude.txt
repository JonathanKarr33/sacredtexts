## Blocking issue: the mark set covers the *expected* side but not the *answer* side

The set was derived from QUL — which is right for expected text — but the answer side is **uncontrolled** (that's the whole point of the search-on arm). Arabic combining marks outside the QUL set still split words mid-word, which is the exact failure mode the spec names. Verified:

```
U+0617 SMALL HIGH ZAIN   الر‹mark›حمن → 'الر حمن'  (plain: 'الرحمن')  equal: False
U+0618/0619/061A SMALL FATHA/DAMMA/KASRA → same split
U+0656 SUBSCRIPT ALEF, U+0657, U+0658, U+065F → same split
U+08F0/08F1/08F2 OPEN FATHATAN/DAMMATAN/KASRATAN → same split
```

`U+0617–U+061A` in particular appear in other Uthmani digitizations alongside the `U+06D6–U+06ED` block you already handle. Because the headline is `correct = normalized` (**whole-string** equality), one such mark anywhere in a retrieved ayah zeroes the item — silently depressing the search-on arm in Phase 3, the single paid phase, in a committed public artifact meant to demonstrate the benchmark's thesis. The spec criterion reads "removes the Arabic- and Hebrew-range combining marks **and** the Qur'anic annotation marks … actually present in QUL" — the first conjunct isn't fully met.

Fix is one line and provably Latin-safe: keep the explicit list (you still need it for the non-`Mn` members `U+0640` Lm, `U+06DE`/`U+06E9` So, `U+06E5`/`U+06E6` Lm) and additionally delete any `category == "Mn"` codepoint in the Arabic/Hebrew blocks (`U+0590–U+08FF`, plus `U+FB1D–U+FB4F`). That is a strict superset of today's behavior, scoped to those blocks, so the Latin regression fixture and the 224k-entry invariance still hold. Add a parametrised test over the handful of codepoints above.

## Non-blocking comments

1. **Test helper `_MARK` diverges from the implementation** (`test_normalize_nonlatin.py:35`). It spans `U+064B–U+0670` (sweeping in Arabic-Indic digits `U+0660–U+0669`) and `U+0591–U+05BE` — i.e. it **deletes** the maqaf while the implementation maps it to a space. It passes only because neither fixture contains a maqaf (I checked: 0 of 1,555 Shevuot lines, 0 QUL ayat). If the selected line ever changes, `normalize(line) == normalize(_strip_combining(line))` fails spuriously for a reason that isn't a real defect. Either reuse `score._SCRIPT_MARKS_RE` for the stripper and handle maqaf→space explicitly, or add a comment pinning why the divergence is safe.
2. **Module docstring is now stale.** `score.py:7-8` still describes `normalized` as "unicode quotes/dashes folded, case-folded, punctuation stripped, whitespace collapsed". Script-mark folding is part of the documented metric contract now and should appear there (the inline comments are good, but the docstring is the contract surface).
3. `test_rescoring_committed_run_reproduces_scores` compares **sorted** lines while the docstring says "byte-for-byte". `score_file` preserves input order, so an unsorted compare would be strictly stronger and still pass — or soften the docstring.
4. **Phase 3 heads-up (not a Phase 1 defect):** deleting `U+0670` is right for QUL↔bare-consonant, but a model spelling `الرحمان` (explicit alef) rather than `الرحمٰن` still mismatches, as do alef-maksura/ya and ta-marbuta/ha variants. Those are orthographic-variant issues beyond this phase's scope — just worth expecting in the Phase 3 numbers rather than reading them as a normalisation bug.
