### The one substantive problem: the README misreports the central finding

The run `README.md` is a Phase 3 deliverable whose job is making the contrast readable. Its causal analysis is contradicted by its own committed data.

The README concludes **"web search did not improve strict-reference accuracy, and slightly reduced it"** and attributes the Qur'an drop to *orthographic variance* ("retrieve the Arabic text in a slightly different vocalisation... normalisation deliberately does not rewrite letter choices"). I tested that claim by checking whether each regressed answer *contains* the normalize-equal reference text:

- **haiku-search Qur'an regressions: 10 of 11 contain the exact reference text.** Only 1 is a genuine text difference. These scored 0 for appended prose, **not** orthography.
- **The opus right→wrong flip** (`retrieve_quote-642fbf516c7a`): the quoted line is `normalize`-equal to the expected text — the only raw deltas are harakat ordering, which Phase 1 correctly folds. It scored 0 solely because of a trailing English disclaimer. The README calls this "ordinary sampling variation"; it's a wrapper penalty on a perfect retrieval.
- **Most important — the Talmud claim is inverted.** The README says "all four entries score ~0%... web search does not lift this." In fact **opus-search contains the exact Aramaic reference in 8 of 34 cells (~24%) vs. 0 of 34 for opus-off**, and produced substantially-Hebrew answers in 11 of 34 vs. 0. Web search lifted Talmud retrieval from nothing to ~24%; the headline hid it because the model wrapped the quote (plausibly citing Sefaria — *because* it searched).

Across the run, **20 of 400 cells score 0 while containing the exact reference text**, concentrated in the search-on entries. That asymmetry *is* the result.

This is exactly the hazard the spec mandated be surfaced — "a search-on answer that appends an attribution/citation can score *lower* on the headline while retrieving better; `token_f1`/`exact` are named as the discriminating numbers." The README names it generically under "Reading the scores," but the section a reader actually trusts asserts the opposite mechanism. For a public benchmark whose stated motivation is credibility, shipping an interpretation its own data refutes is the wrong thing to commit.

**This is a documentation fix only — no re-collection, no re-scoring, no code change, and no spend.** The numbers above are recomputable from the committed artifacts. Do **not** alter `_SUBMETRICS` or the headline rule (spec requirement 4 forbids it) — the headline is working as designed; it's the prose that needs to match it.
